Product Requirements Document

Super-Manner：可授权、可验收、可自我迭代的协作 Coding Agent

架构师提交目标与验收标准，系统自行组队、分工、执行、验证，交付可审查的代码与证据；每次交付后，团队依据评测结果变强一点。

版本 v0.1（评审稿） 状态 待评审 范围 P0 定义 更新 2026-11-03 负责人 [TBD]

01背景与问题

现有的 coding agent 已经能完成单点任务：读代码、改文件、开 PR。但一旦把视角从“一个任务”抬到“一个目标”，三个问题会同时出现。

观察到的现象根因产品响应
Agent 能改对一个函数，但接不住“把邀请功能做完”委派单元是任务，不是目标；缺少拆解、依赖与完成定义引入目标契约与计划确认，目标成为唯一委派单元
多个 Agent 聊得很热闹，最后没人说得清做到哪了把对话当成了状态，缺少结构化账本与证据聊天只做协调，状态、产物、证据进账本
敢让它写代码，不敢让它合并、改配置、碰密钥边界靠提示词，权限一次授予、长期有效动作级授权，随目标签发与失效，越界由运行时拒绝
这次跑得好，下次还可能犯同样的错没有复盘与评测，经验停留在人脑里复盘产出版本化提案，离线评测后灰度生效

受影响的人是架构师与技术负责人：他们不缺会写代码的 Agent，缺的是一个可以放心委派目标、并且只需要在关键点出现的协作体。

产品判断
自主性不是“让 Agent 更敢做”，而是同时具备三件事：目标所有权（自己决定怎么做）、可验证的完成（证据定义完成）、可回滚的授权（越界必须升级）。缺任何一项，自主性都会变成风险。

02目标与用户

2.1 目标用户

角色核心诉求在本产品中的位置
架构师（主用户）把一整块工作交出去，只在计划、越界、验收三个点出现目标的所有者与授权的签发者
开发者提交小目标、查看进度、参与验收目标提交人；在授权范围内同样可签发
Agent 维护者调整角色契约、提示词与技能，且改动可控Playbook 的维护者，参与迭代评审
观察者了解进展，不介入只读：房间、看板、证据

2.2 产品目标

  • 架构师用一次目标委派替代一串指令，最终拿到可审查的 PR 与完整证据。
  • Agent 在授权范围内自主决策，越界时停下来问，而不是绕过去。
  • 每个目标结束后，系统能给出可评测、可回滚的改进提案。
  • 简单任务不被组织开销拖慢：默认可以使用单 Agent。
不追求
不追求“全自动软件公司”。P0 的终点是可验收的 PR，不是自动发布；是受控的自我改进，不是无人监督的自我复制。

03范围

3.1 P0：最小完整旅程

P0一次目标，一个仓库，到 PR 为止
  1. 提交目标：仓库、基线、验收标准、约束、预算、自治级别。
  2. 确认计划：系统给出拆解、角色、依赖、预算分配与风险点，人批准或修改。
  3. 签发授权：按目标签发动作级 Grant，明确能读什么、写什么、能开到哪一级。
  4. 执行：Builder 在隔离工作区实现，产物为分支、提交与 PR。
  5. 越界裁决：超出 Grant 的动作被运行时拒绝，需要时生成升级卡片请人裁决。
  6. 独立验证：Verifier 在干净上下文中按验收标准逐条验证，产出证据。
  7. 人工验收：人看目标、差异、证据、风险，做一次接受或返工决定。
  8. 归档与复盘：目标结束，授权全部失效；生成复盘记录。

3.2 P1：紧随其后

  • 多子任务并行、依赖合流与冲突处理。
  • 跨仓库目标（同一组织内的多个仓库）。
  • “挣来的自治”：连续通过验收后，按动作类别小幅提升授权。
  • 团队知识：跨目标的经验沉淀、引用与撤回。

3.3 明确排除

  • 自动发布到生产环境（`release.deploy` 始终需要人）。
  • 多租户、计费、组织级权限体系。
  • 移动端与独立 IDE 插件。
  • 让 Agent 修改自己的权限、预算上限或验收标准。

04产品模型

4.1 角色

角色不是人格设定，而是能力契约。同一套契约可以实例化多个 Agent，也可以由人临时承担。

角色对什么负责关键产出不能做什么
架构师目标是否值得做、验收是否通过目标契约、授权、验收决定不直接改代码
负责人（Planner）把目标拆成可执行、可验证的工作项计划、依赖图、角色与预算分配不写业务代码、不合并
实现者（Builder）在授权范围内完成工作项分支、提交、PR、实现说明不改 CI 配置、不合并、不碰密钥
验证者（Verifier）独立判断是否达到验收标准逐条结论、证据、返工建议不修代码、不与实现者共享上下文
观察者知情无不做任何改变状态的操作

每个角色实例都由一份角色契约定义：目标、范围与非目标、输入、产出结构、退出条件、授权、升级触发条件、交接格式。契约随目标版本化，改动需走迭代流程。

4.2 核心对象

对象含义关键字段
Goal一次委派的目标，唯一入口描述、仓库与基线、验收标准、约束、预算、自治级别、状态
Plan目标的版本化拆解工作项、依赖、角色、预算分配、风险、待决点
WorkItem可独立执行与验证的最小单元负责人、依赖、完成定义、状态、关联产物
Run一次角色实例的执行实例、工作区、预算消耗、起止时间、结果
Artifact可审查的产物分支、提交、PR、文档、差异摘要
Evidence支撑“完成”的事实命令、输出、环境、时间、哈希、逐条验收结论
Grant授权书主体、动作集合、资源范围、约束、级别、签发人、状态
Escalation越界裁决请求动作、资源、理由、影响、备选、推荐、裁决结果
Decision需要留痕的判断问题、选项、决定、依据、决定人
Playbook角色行为的版本化载体提示词、技能、检查清单、适用条件、版本、评测结果
Room / Message协调层房间、成员、消息、引用对象、已读水位
唯一真相
Room 只承载协商，不承载状态。 任何影响目标推进的结论，必须落到 Decision、WorkItem 或 Evidence 上；聊天记录可以作为引用，但不能作为唯一依据。

4.3 生命周期

Goal

状态进入条件可执行的动作
草稿目标已提交，必填项待补齐补全、删除
待确认计划已生成批准、修改、拒绝
执行中计划批准且授权已签发暂停、取消、裁决升级
验证中全部工作项进入验证查看证据、取消
待验收验证结论为通过接受、返工、关闭
已完成 / 失败 / 已取消终态查看、归档、发起复盘

WorkItem

排队 → 执行中 → 等待人（阻塞/升级）→ 验证中 → 已接受 / 待返工 / 失败 / 已取消。终态之外的状态都必须能回答“现在在等谁”。

Grant

待生效 → 生效 → 暂停 → 已撤销 / 已过期。目标进入终态时，其下所有 Grant 一并失效，正在执行的 Run 在有限时间内停止。

05功能需求

本章按任务组织。编号稳定，供评审、实现与验收引用；每条需求都覆盖触发、规则、结果与状态变化。

FR-01目标提交与目标契约P0
目的
让架构师用一次结构化委派，替代一串上下文不完整的指令。
触发
架构师或授权开发者从仓库、协作房间或控制台提交目标。
字段
  • 目标描述（必填）：要达成的业务或工程结果，不是实现步骤。
  • 仓库与基线（必填）：仓库标识、基线分支、禁止改动的路径。
  • 验收标准（必填）：至少一条可机器或可人工判定的条件。
  • 约束（选填）：依赖版本、兼容性、性能、安全、风格。
  • 预算上限（必填）：以 [TBD: token 或金额] 计。
  • 自治级别（必填，默认 A2）：见 6.2。
  • 交付期限（选填）。
规则
  • 缺少验收标准、预算上限或仓库基线时拒绝创建，并指出缺失项。
  • 仓库不在允许列表内时拒绝创建。
  • 同一仓库出现高度相似的在途目标时，提示关联到已有目标，而不是新建。
  • 提交人不具备该仓库的授权资格时，目标进入草稿并提示可用的签发人。
结果与状态变化
目标创建为草稿；资料齐备后自动进入待确认，并触发计划生成。
异常
提交过程中会话中断时，已填写内容保留为草稿，不自动提交。
FR-02计划生成与人工确认P0
目的
在动手之前对齐“做什么、谁来做、做到什么程度”，避免昂贵的返工。
触发
目标进入待确认。
计划内容
  • 工作项清单：每个工作项的目标、完成定义、负责人角色。
  • 依赖关系与可并行部分。
  • 预算分配：合计不得超过目标预算。
  • 风险与待决点：需要人现在决定的事项。
  • 验证方式：谁来验证、验证哪些标准。
规则
  • 计划不得超出目标的范围与约束；超出时必须在计划中标明并请求扩权。
  • 派生的角色权限必须是目标授权的子集，不得放大。
  • 人可整体批准、逐项批准、修改后再批准，或拒绝并说明原因。
  • 被拒绝的计划不得原样重提；必须体现修改或新增信息。
结果与状态变化
批准后目标进入执行中，按批准范围签发授权；拒绝后目标回到草稿或终止。
异常
超过 [TBD] 未确认时保持待确认，不自动开始执行。
FR-03授权签发P0
目的
把“相信 Agent 会遵守”换成“Agent 拿不到就越不了界”。
触发
计划批准时自动生成建议授权；人确认后生效。
授权内容
主体、允许的动作集合、资源范围、约束（预算、改动行数、时效、网络白名单）、自治级别、签发人、父授权。
规则
  • 只有人类主体可以签发授权；Agent 只能申请，不能签发或转授。
  • 未匹配到任何授权的动作一律拒绝。拒绝不是异常，是正常结果。
  • 授权随目标存续：目标结束、失败或取消时全部失效。
  • 派生 Agent 的授权必须由父授权推导且不大于父授权。
  • 授权不得续期；需要更长时间时重新签发。
结果与状态变化
授权生效并写入审计；工作项获得对应动作的执行能力。
异常
授权被撤销时，正在执行的相关动作在下一次校验点失败，Run 进入等待人状态。
FR-04越界与升级裁决P0
目的
让 Agent 在边界上停下来问人，而不是绕过或静默放弃。
触发
动作已在授权内但超出约束（预算、行数、路径、时效），或该动作需要第二人确认。
升级卡片字段
请求的动作与资源、原因、影响面、备选方案、推荐选项、风险说明、预算影响、有效期限。
规则
  • 未授权的动作直接拒绝，不生成卡片；只有“有资格但超限”才升级，避免审批疲劳。
  • 同一目标下的同类请求聚合为一张卡片。
  • 批准只对本次具体动作有效，用后即失效。
  • 超时未裁决时目标暂停，等待人；不得自动放行，也不得自行寻找替代路径绕过。
  • 被拒绝后，Agent 必须改方案或报告阻塞；同一请求在无新信息时不得重复提交。
结果与状态变化
批准后动作执行并留痕；拒绝后相关工作项进入阻塞并说明原因。
异常
裁决人失去该仓库权限时，请求重新路由给其他合格签发人。
FR-05组队与角色实例化P0
目的
按任务复杂度组建合适规模的团队，而不是默认越多越好。
触发
计划批准后，按工作项实例化角色。
规则
  • P0 至少包含实现者与验证者，且二者为不同实例、不同上下文。
  • 单文件或单验收项的小目标，允许“单实现者 + 验证者”，不强制组建完整团队。
  • 新增角色必须由负责人申请，受 agent.spawn 授权约束，且权限衰减。
  • 角色实例失败后不得由同一实例给自己“补考”；重试必须换实例或换策略。
结果与状态变化
每个实例获得独立工作区、独立预算区间与独立授权副本。
异常
并发或预算不足时，低优先级工作项排队，不得挤占验证者的资源。
FR-06执行与工作区隔离P0
目的
让多个工作项可以安全并行，互不污染、互不覆盖。
触发
工作项进入执行中。
规则
  • 每个工作项使用独立工作区，基线只读，产物落在独立分支。
  • 实现者只能看到本工作项的输入与授权，不读取其他在途工作项的未完成产物。
  • 不得修改基线、不得强制推送、不得改动超出授权路径的文件。
  • 凡是产物，必须形成可审查的差异与提交记录；口头描述不算产物。
结果与状态变化
工作项进入验证中时，必须已有可访问的产物与自测证据。
异常
工作区创建失败或环境不可用时，工作项进入等待人，不消耗重试次数，也不产生“已完成”的假象。
FR-07协作房间与唤醒P1
目的
让多个 Agent 与人可以协商接口、认领任务、报告阻塞，但不把对话变成状态。
触发
计划中存在跨工作项的接口或依赖时，自动创建房间并邀请相关实例。
规则
  • 每条消息必须引用工作项编号；无引用的消息不进入决策记录。
  • 通知只用于唤醒空闲实例；被唤醒的实例必须回到自己的任务上下文。
  • 只推送三类消息：阻塞、需要决策、完成。其余静默。
  • 人可以在房间旁观与插话；人的发言视为对该目标的直接指令，但仍受授权约束。
  • 关键结论必须落为 Decision；聊天记录只能作为引用。
结果与状态变化
协商结果改变工作项的依赖、接口约定或阻塞状态，并留下引用。
异常
房间成员不足或长期无人回应时，负责人升级给人，不自行假设对方同意。
FR-08独立验证与证据P0
目的
让“完成”由事实支撑，而不是由实现者自己的判断支撑。
触发
实现者提交产物并声明可验证。
输入
目标的验收标准、产物差异、仓库与环境。验证者不接收实现者的推理过程与自我评价。
必须执行
  • 逐条给出验收标准的结论：通过 / 不通过 / 无法判定。
  • 运行约定的检查与回归，记录命令、输出、环境、时间与产物哈希。
  • 检查变更影响面：是否触碰禁止路径、是否引入未声明的依赖。
规则
  • 证据缺失即判定不通过，不允许“看起来没问题”。
  • 验证者不得修改代码；发现问题时提出返工要求，而不是顺手修掉。
  • 验证者与实现者必须是不同实例，且不共享上下文。
  • “无法判定”必须转成给人处理的问题，不得默认算通过。
结果与状态变化
全部通过则目标进入待验收；存在不通过项则相关工作项进入待返工，并附具体理由。
异常
验证环境自身不可用时，标记为环境阻塞，不计入实现者的失败次数。
FR-09人工验收与结束P0
目的
把最终判断权留给人，同时让人只看必要信息。
触发
目标进入待验收。
验收视图
目标与验收标准、变更摘要与关键差异、逐条证据、风险与未决项、预算消耗、需要人知道的偏差。
动作
  • 接受：目标完成，授权失效，产物保持可访问。
  • 返工：必须填写理由；生成新的工作项，继承原授权或收窄，历史记录保留。
  • 关闭：目标终止，说明原因，不影响已产生的产物。
规则
  • 一次验收只做一个决定；需要拆分时先拆子目标。
  • 验收人必须是该仓库的授权主体；不能由实现者或验证者代签。
  • 产物在验收前被外部合并或关闭时，系统提示该事实，不自动判定为通过。
结果与状态变化
目标进入终态，生成复盘记录；返工时目标回到执行中。
异常
验收人长期不处理时，目标保持待验收并进入提醒队列，不自动接受。
FR-10暂停、取消与失败恢复P0
目的
让“停下来”和“出错了”都是确定、可恢复的状态，而不是失控。
触发
人主动暂停或取消；执行失败；预算耗尽；环境中断。
规则
  • 暂停：停止新的动作，保留工作区与上下文，可恢复。
  • 取消：立即失效全部授权，停止运行中的实例，保留产物与审计，不可恢复。
  • 同一原因连续失败两次后转为人处理；不得无限重试。
  • 预算耗尽时暂停并升级，不允许“借预算”继续。
  • 结果未知的外部副作用（例如已发出但未确认的写操作）不得自动重试。
结果与状态变化
目标、工作项与授权同步进入对应状态；取消后所有派生实例与工作区在有限时间内清理。
异常
清理失败时保留记录并告警，不掩盖残留。
FR-11复盘与自我迭代P1
目的
让团队在每次交付后变强一点，且这种变化可评测、可回滚。
触发
目标进入终态后自动生成复盘；也可由人手动发起。
复盘内容
结果与预期偏差、人工介入点、升级与拒绝记录、失败原因、预算消耗、可复用的经验。
允许的提案
角色契约与提示词、检查清单、技能库、任务拆解策略、路由规则、测试用例。
禁止的提案
权限与授权规则、预算上限、验收标准、验证器本身、审计记录。
流程
  1. 提出变更包：差异、假设、预期收益、影响面。
  2. 在留出的黄金任务集上回放，必须证明“不下降，且至少一项改善”。
  3. 小范围灰度生效，观察结果与偏差。
  4. 晋升或回滚；高风险变更必须由人批准。
规则
  • 未通过评测的变更不得上线，不得以“先试试”为理由绕过。
  • 上线后关键结果恶化时自动回滚，并保留现场。
  • Agent 不能修改评估集、评估标准或自己的权限。
  • 每次变更必须能回答：改了什么、为什么、证据是什么、如何回滚。
结果与状态变化
生成新版本的 Playbook，旧版本保留可回退；变更记录进入审计。
异常
评测环境不可用时保持原版本，不降级为“人工口头判断”。
FR-12审计、追溯与待我处理P0
目的
任何一次交付都能回答“谁、凭什么、做了什么、结果如何”。
记录范围
目标的创建与变更、计划批准、授权签发与失效、每一次放行与拒绝、升级与裁决、验证证据、验收决定、迭代上线与回滚。
规则
  • 审计只追加，不可删除、不可静默修改；纠错以新增记录表达。
  • 每条记录包含主体、时间、动作、资源、依据（哪条授权或哪次裁决）。
  • “待我处理”只呈现三类：待确认计划、待裁决升级、待验收结果。
  • 队列项必须显示等待时长与卡住的原因，而不只是一个状态标签。
结果与状态变化
人可在任意时刻还原一个目标的完整决策链。
异常
审计写入失败时，相关动作不得继续执行。

06共享规则

以下规则对全部功能需求生效，不重复写在单条需求里。出现冲突时，以本章为准。

6.1 权限矩阵

本表约束的是系统授予 Agent 角色的动作能力。人类主体的仓库权限由代码托管平台决定，系统只额外约束其能否签发授权。

为什么用动作而不是角色授权
角色会变、实例会换、提示词会被改写，只有动作 + 资源 + 约束是可校验的。系统在每次工具调用前比对授权，不依赖 Agent 是否“记得”规则；未匹配即拒绝，拒绝是正常返回值，不是错误。

6.2 自治级别

自治级别是上限，不是默认放行。级别为 A3 不代表可以合并任意 PR，具体动作仍需对应的 Grant 覆盖。

级别名称可自主完成必须停下来问
A0只读建议读代码、分析、给出方案与差异建议一切写操作；连评论也需人代发
A1提方案在 Issue 或房间内讨论、写方案文档、产出补丁草案开分支、推送、开 PR
A2写分支开 PR
（默认）		写自有分支、提交、推送、开 PR、回应评审意见合并、改 CI 配置、读密钥、跨仓库操作
A3合并小改动在行数、文件数、路径白名单与 CI 通过等限额内合并超出限额、触碰敏感路径、发布
A4发布运维预发部署、灰度、回滚、跑运维脚本生产发布、改权限、改预算、改基础设施配置

级别只能由人设定或调整，且调整本身进入审计。Agent 可以提出“希望提升到 A3”的建议，但不能自行生效。

6.3 完成定义

完成不是状态字段，而是证据集合的结论。三个层级分别定义：

层级必须同时满足判定人
工作项完成产物可访问；自测证据齐全；未触碰禁止路径；验证者逐条给出结论且无“不通过”验证者
目标完成全部工作项已接受；验收标准全部有结论；无未决升级；预算未超限；人已作出接受决定验收人
交付完成PR 已按授权合并或明确交由人合并；复盘记录已生成；授权已失效系统 + 验收人

证据的最低要求

  • 可复现：给出命令、环境与依赖版本，他人能重跑。
  • 可核对：附输出摘要与产物哈希，而不只是“已通过”。
  • 可归属：记录执行者实例、时间与所依据的验收标准条目。
不许用“看起来没问题”结案
证据缺失一律判为不通过；“无法判定”必须转成给人处理的问题，不得默认算通过，也不得由实现者补充自评后重新计数。

6.4 升级规则

情况系统行为理由
动作不在任何 Grant 内直接拒绝，不生成卡片，返回拒绝原因无资格不是“超限”，问人只会制造审批噪音
动作在 Grant 内但超出约束暂停该动作，生成升级卡片有资格但超限，人的一次判断即可放行
高风险动作需第二人确认路由给第二名合格签发人单点判断不足以承担该类风险
同一目标出现多个同类请求聚合为一张卡片，列明各项避免同一类问题反复打断人
批准后执行仅对当次动作、当次资源有效，用后失效批准是判断，不是长期授权
超时未裁决目标暂停并保持等待不自动放行，也不许绕路
被拒绝且无新信息拒绝重复提交，要求改方案或报告阻塞防止用重试消耗人的注意力
裁决人失去该仓库资格重新路由给其他合格签发人授权链不能停在失效主体上

6.5 迭代红线

以下六条对任何角色、任何级别、任何自动化流程都成立。触碰任一条，相关变更自动失效并升级给人。

  1. 不得修改评估集、验证器或验收标准，使自己的产出更容易通过。
  2. 不得为自己或同伴提升权限、扩大预算、放宽网络与密钥范围。
  3. 不得删除、改写或选择性忽略失败、拒绝与回滚记录。
  4. 不得跳过评测直接上线，也不得以“先灰度试试”替代评测。
  5. 不得由同一实例既提出变更又批准变更。
  6. 不得派生无父授权、无预算、无回收期限的常驻实例。
红线的执行方式
红线不是提示词里的劝告，而是运行时校验：变更包的字段中若包含权限、预算、验收标准或评估集，提交即被拒绝；审计表对写入方只开放追加。

07关键流程

流程描述的是正常路径下的责任交接，异常分支见第 8 章。每个步骤都要有明确产出物，没有产出物的步骤视为未发生。

7.1 一次典型交付

T0 提交
架构师提交目标：仓库与基线、验收标准、约束、预算、自治级别。 → Goal（草稿→待确认）
T1 计划
负责人拆解工作项、依赖、角色、预算与风险，标出需要现在决定的事项。 → Plan v1
T2 确认
架构师批准、修改或拒绝。批准即表示认可范围与预算分配。 → Decision
T3 授权
按批准结果签发动作级 Grant，并按工作项派生、只减不增。 → Grant 集合
T4 执行
实现者在独立工作区完成工作项，产物为分支与提交，期间不触碰禁止路径。 → Artifact
T5 自检
实现者跑通约定检查，提交 PR 与自测说明，声明可验证。 → PR + 自测证据
T6 验证
验证者在干净上下文按验收标准逐条判定，记录命令、环境与哈希。 → Evidence + 结论
T7 验收
架构师看目标、差异、证据与风险，做接受、返工或关闭。 → Decision
T8 归档
授权全部失效，产物保持可访问，生成复盘记录。 → Review + 审计
人只出现在三个点
T2 确认计划、T7 验收结果，以及期间的越界裁决。其余时刻人可以旁观，但不被要求持续盯着进度；系统的默认行为是继续推进或明确停下等人，而不是频繁询问。

7.2 越界裁决

① 拦截
工具调用前校验动作、资源与约束，命中即拦截并返回结构化原因，实例不获得部分执行。
② 归因
区分“无授权”与“超约束”：前者直接拒绝并结束；后者进入升级。
③ 组卡
生成升级卡片：动作、资源、原因、影响面、备选方案、推荐项、预算影响、有效期限。
④ 裁决
合格签发人批准（限当次）、拒绝（须给理由）或要求补充信息。
⑤ 执行
批准后仅执行该次动作，用后失效；拒绝后工作项进入阻塞并说明原因。
⑥ 留痕
记录请求、依据、裁决人、结果与耗时，供复盘统计升级热点。

若实例在等待期间发现另一条不越界的路径，可以改道执行，但必须在记录中说明改道原因；不得静默绕过原请求。

7.3 失败与恢复

场景判定系统动作恢复方式
实现失败构建、测试或运行报错记录失败证据，同实例有限次重试换策略重试；两次同因失败转人
验证不通过存在“不通过”项工作项转待返工，附具体条目与证据新 Run 返工，历史结论保留
环境不可用工作区或依赖无法创建标记环境阻塞，不消耗实现者失败次数环境恢复后从检查点继续
预算耗尽消耗达到分配上限暂停并升级人追加预算或收窄范围
授权撤销下一次校验点失败停止相关动作，Run 转等待人重新签发或取消目标
产物被外部改动基线或 PR 被他人更新提示冲突事实，不自动覆盖人决定变基、重做或放弃
外部副作用未知写操作已发出但未确认不自动重试，标记待核对人工核对后决定继续或回滚

共同原则：失败必须留下证据、必须能回答“现在在等谁”、必须允许人不带上下文地接手。

7.4 一次进化提案

① 复盘
目标终态后汇总：偏差、人工介入点、拒绝与升级、失败原因、预算消耗。 → Review
② 提案
只能改角色契约、提示词、检查清单、技能、拆解策略、路由规则、测试用例。 → Change Set
③ 回放
在留出的黄金任务集上对比新旧版本，要求“不下降，且至少一项改善”。 → 评测报告
④ 灰度
小范围启用新版本，观察关键结果与偏差，保留随时回退的开关。 → Canary
⑤ 晋升
达标则晋升为新默认版本；恶化则自动回滚并保留现场。 → Playbook vN+1
高风险变更必须由人批准
涉及路由规则、验证阈值、任务拆解策略的变更会改变系统的整体行为，即使评测通过也必须由人确认；其余变更可由系统在评测与灰度达标后自动晋升，并事后通知。

08异常与边界

本章列出必须被显式处理的情形。判定标准不是“有没有报错”，而是状态是否诚实、是否可恢复、是否留下证据。

情形期望行为不得发生
目标信息不完整保存为草稿，逐项指出缺失字段与可补全的人用默认值替人做决定后开始执行
两个目标改同一片代码提示冲突范围，建议合并目标或错开执行双方并行改同一文件后互相覆盖
计划与目标范围冲突在计划中标红并请求扩权或缩范围先做后报，等验收时才发现超出授权
验收标准无法判定转成给人处理的具体问题，目标保持待验收由实现者自评后算通过
长时间无人裁决目标暂停，队列显示等待时长与卡点超时自动放行或自动降级执行
取消目标授权立即失效，运行实例停止，产物与审计保留清理不彻底却标记为已取消
授权在运行中失效下一校验点停止，未完成的写操作不重试用已缓存的凭据继续完成当前步骤
证据缺失或损坏判定不通过，要求重跑并说明沿用上一次的通过结论
预算耗尽暂停并升级，说明已产生的价值与剩余工作自行压缩验证步骤以省预算
环境或依赖中断标记环境阻塞，保留检查点把环境问题计入实现者失败次数
PR 被外部合并或关闭如实提示，交人判断是否仍满足验收标准因“已合并”自动判定目标完成
迭代后指标恶化自动回滚到上一版本并保留现场继续观察一段时间再说
一条底线
宁可停在“等待人”，也不要停在“看起来完成了”。 所有模糊情形一律向“保留状态、请求判断”收敛，而不是向“继续执行”收敛。

09观测与验收

本产品自身也需要被验收。原则是：看人是否更省力、看状态是否可信，而不是看 Agent 写了多少代码。

9.1 可观察信号

维度信号用途
自主性每个目标的人工介入次数判断是否只在计划、越界、验收三点出现
无人工干预直达待验收的比例判断目标所有权是否真的交出去了
升级请求中“有资格但超限”的占比过高说明授权过窄，过低可能说明授权过宽
可靠性首次验证通过率衡量实现质量与自检有效性
平均返工次数与返工原因分布定位是理解偏差、实现缺陷还是标准不清
未授权动作的实际拦截次数验证边界是否真的在运行时生效
效率目标从提交到待验收的耗时分布识别计划、等待裁决、验证哪一段最慢
预算实际消耗与计划分配的偏差校准拆解与估算
进化迭代提案的评测通过率与回滚率判断自我改进是真实有效还是噪声
变更上线后关键信号的偏移确认改进没有以别处退化为代价

本版不承诺具体数值目标。基线需在 P0 试运行后按真实数据确定，目标值与告警阈值在评审时补充 [TBD]。

9.2 验收方式

P0 的验收不看功能清单是否全部点亮，而看以下五条是否同时成立：

  1. 架构师只凭验收视图就能做出接受或返工决定，无需再向 Agent 追问背景。
  2. 换一个人接手，能仅凭审计记录还原“谁、凭什么、做了什么、结果如何”。
  3. 取消一个目标后，其授权确实失效，没有残留实例继续动作。
  4. 整个试运行期间，没有一次未授权动作被执行。
  5. 至少有一次进化提案完整走完“评测 → 灰度 → 晋升或回滚”。
失败信号
出现下列任一情况即视为不达标：需要人持续盯进度才有推进；验收时需要口头解释才能理解证据；Agent 绕开拒绝换条路继续做；复盘结论无法追溯到具体记录。

11.1 与参考实现的取舍

本产品不直接复用下列项目的代码或协议，只借鉴其被验证过的模型。

能力参考来源在本产品中的形态
事件入口与工单生命周期dsh-superagent-prototype外部事件进入后形成目标与工作项；状态由事实派生，不靠人工改标签
隔离执行dsh-superagent-prototype每个工作项独立工作区与独立会话，产物落独立分支
组织与依赖multi-agent-team工作项依赖、角色契约、预算分配、独立验证与证据
协调层opencode-chat-room房间、唤醒、已读水位、人机同群；只协商，不承载状态
组织学习本产品新增复盘 → 提案 → 黄金任务集评测 → 灰度 → 晋升或回滚

三者互补但都不完整：前者强在入口与生命周期，中者强在组织与证据，后者强在通信；缺的正是把交付结果转化为受控改进的那一层。

11.2 术语

术语含义
目标（Goal）一次委派，包含验收标准、约束、预算与自治级别，是唯一入口
工作项（WorkItem）可独立执行与验证的最小单元，必须能回答“现在在等谁”
授权（Grant）动作、资源、约束的组合，随目标签发与失效，不可转授
升级（Escalation）有资格但超限时请求人裁决，一次一用
证据（Evidence）可复现、可核对、可归属的事实，是“完成”的唯一依据
Playbook角色行为的版本化载体，变更需经评测与灰度
自治级别A0–A4，表示允许自主推进的上限，不是默认放行
黄金任务集留出的、不参与日常优化的评测任务集合，用于比较版本
权限衰减派生授权的范围只能小于或等于父授权
完成定义（DoD）工作项、目标、交付三层各自的完成条件，全部以证据判定
